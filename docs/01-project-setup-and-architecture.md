What was built, why each decision was made, and the v16-specific traps found
along the way.

## 2. Folder structure

```
src/
├── app/                      Routing ONLY — a file here is a URL
│   ├── layout.tsx            Root layout: fonts, metadata, header/footer
│   ├── page.tsx              Home
│   ├── error.tsx             Route error boundary ("use client")
│   ├── not-found.tsx         404 UI
│   ├── globals.css           Tailwind v4 theme + design tokens
│   ├── products/
│   │   ├── page.tsx
│   │   └── [slug]/page.tsx
│   ├── categories/
│   │   ├── page.tsx
│   │   └── [slug]/page.tsx
│   └── about/page.tsx
│
├── components/               Cross-feature, presentational
│   ├── ui/                   Primitives: button, card, badge, container
│   └── layout/               site-header, site-footer
│
├── features/                 Vertical slices — the real application code
│   └── catalog/
│       ├── types.ts          Domain contracts
│       ├── data/seed.ts      In-memory "database"
│       ├── server/           Server-only data access
│       │   └── catalog-repository.ts
│       └── components/       Catalog-specific UI
│
├── config/site.ts            Site name, URLs, navigation
└── lib/                      Framework-agnostic helpers
    ├── env.ts                Validated environment variables
    └── utils.ts              cn(), formatPrice(), slugify(), sleep()
```

**The rule that makes this work:** `src/app/` is a routing table, not a place
to put code. Anything that is not a route lives in `features/`, `components/`,
`lib/` or `config/`. A page's job is to compose — fetch via a repository,
render components, nothing else.

**Why `features/` over a flat `components/` + `lib/`:** a flat layout forces
every new file into a global namespace, and by topic 13 that is unnavigable.
Vertical slices keep catalog code together, so the cart/checkout/reviews slices
added later do not interleave with it.

**Dependency direction** — strictly one-way, which is what prevents cycles:

```
app/  →  features/  →  lib/, config/
  ↓         ↓
components/ ←┘
```

## 3. The v16 rules that actually bite

### `params` and `searchParams` are Promises

Synchronous access was deprecated in v15 and **removed** in v16.

```tsx
export default async function Page(props: PageProps<"/products/[slug]">) {
  const { slug } = await props.params; // await is mandatory
}
```

`PageProps<"/products/[slug]">`, `LayoutProps<"/">` and `RouteContext<...>` are
globals generated by `next typegen` (which `next dev` and `next build` run
automatically). The route string is checked against the real route tree — a
typo is a compile error.

### `cacheComponents: true` changes the default

This is on in this project. It enables Partial Prerendering everywhere and
makes caching explicit. The rule:

> Reading request-time data — `cookies()`, `headers()`, `searchParams`, or an
> uncached `fetch` — is a **build error** unless it is inside a `<Suspense>`
> boundary or behind `use cache`.

Three ways to satisfy it:

1. `<Suspense>` — the value is request-time; stream it.
2. `"use cache"` — the value is cacheable; prerender it into the static shell.
3. Pass it as a prop — read it outside, hand it to a cached function.

Errors you will meet if you get it wrong:

| Error overlay                 | Cause                                      |
| ----------------------------- | ------------------------------------------ |
| `blocking-route`              | Dynamic data, no Suspense and no `use cache` |
| `blocking-prerender-current-time` | `Date.now()` / `new Date()` during prerender |
| `blocking-prerender-random`   | `Math.random()` / `crypto.randomUUID()`    |
| `next-request-in-use-cache`   | `cookies()` / `headers()` inside `use cache` |

> This is why the footer shows no copyright year. `new Date().getFullYear()` in
> a Server Component is exactly `blocking-prerender-current-time`. Rendering it
> needs `await connection()` plus a Suspense boundary, or a `use cache` block
> that accepts the year being frozen at build time.

### `use cache` in the repository

Every read in `catalog-repository.ts` looks like this:

```ts
export async function getFeaturedProducts(limit = 4): Promise<Product[]> {
  "use cache";
  cacheLife("catalog"); // custom profile from next.config.ts
  cacheTag("products", "products:featured"); // invalidation handles
  ...
}
```

- `cacheLife` is imported from `next/cache` — **stable in v16**, no
  `unstable_` prefix.
- Arguments form the cache key, so they must be serialisable. No functions, no
  class instances, no `Date` objects.
- `cacheTag` declares the handles that `revalidateTag()` will use after a
  mutation in Topic 6.

Custom profiles are declared in `next.config.ts`:

```ts
cacheLife: {
  catalog: { stale: 300, revalidate: 900, expire: 86400 },
}
```

The build output confirms they are applied — every catalog route reports
`Revalidate 15m / Expire 1d`.

### `import "server-only"`

The repository imports it at the top. Importing that module from a Client
Component becomes a **build error** rather than a confusing runtime failure —
cheap insurance against leaking a data layer into the browser bundle.

## 4. Two bugs found by actually running the build

Both were caught by smoke-testing the production output, not by the type
checker. Worth recording because neither is obvious.

### `optimizePackageImports` is not a top-level key

It has its own page in the config docs, which makes it look top-level. It is
not — it lives under `experimental`, and setting it at the top level is a type
error. It was removed entirely rather than relocated: `lucide-react` is on
Next's optimised-by-default list, so the setting would have been a no-op.

### Unknown slugs return `200` on the first request

`curl /products/does-not-exist` returns **200 cold** and **404 warm**.
Reproducible, and it is documented, intended behaviour:

> Before streaming starts, Next returns a `404`. After streaming starts the
> status remains `200` and the not-found UI renders. Next injects
> `<meta name="robots" content="noindex">` in both cases.
> — `not-found.md`

Under PPR the static shell is flushed immediately, which fixes the status line
before the streamed segment ever calls `notFound()`.

The reflex fix, `export const dynamicParams = false`, is **rejected** under
`cacheComponents`:

```
Error: Route segment config "dynamicParams" is not compatible with
`nextConfig.cacheComponents`. Please remove it.
```

That rejection is correct — it would pin the catalogue to build time. The
framework's answer is the injected `noindex`, verified present in the cold
response. If a hard pre-stream 404 is genuinely required, reject the slug in
`proxy.ts` before the response starts (Topic 11).

**Knock-on effect:** the root layout originally set
`robots: { index: true, follow: true }`. On a soft-404 that emitted a *second*,
contradictory robots tag next to Next's `noindex`. Crawlers take the most
restrictive directive, so it would probably have been fine — but the tag was
redundant anyway, since indexing is the default. It is gone. Valid pages now
carry no robots tag; only not-found pages carry `noindex`.

## 5. Environment variables

`src/lib/env.ts` parses `process.env` through Zod once, at module load, and
splits server from client:

- `clientEnv` — safe anywhere. Only `NEXT_PUBLIC_*`.
- `serverEnv` — a Proxy that **throws** if read in the browser.

Client variables are referenced as full static literals
(`process.env.NEXT_PUBLIC_SITE_URL`). Next replaces that exact text at build
time; a computed lookup like `process.env[key]` survives the build and silently
evaluates to `undefined` in the browser.

A missing or malformed variable fails loudly with its name attached, instead of
surfacing as `undefined` three layers into a request.

## 6. Tailwind v4

There is no `tailwind.config.js`. Configuration is CSS, in `globals.css`:

```css
@theme {
  --color-brand-600: oklch(0.51 0.2 265);
  --radius-card: 0.875rem;
}
```

Declaring a token **generates the utilities**: `--color-brand-600` creates
`bg-brand-600`, `text-brand-600`, `border-brand-600`; `--radius-card` creates
`rounded-card`. This is why `rounded-[var(--radius-card)]` would be wrong — the
utility already exists.

Semantic tokens (`--color-surface`, `--color-content`) point at light/dark
values in `@layer base`, so `bg-surface` flips with the colour scheme without
any `dark:` variants.

Colours are `oklch()` for perceptually even lightness steps.

### Known issue: 14 high-severity npm advisories

All 14 collapse to one root cause: a ReDoS in `picomatch`, reached through the
ESLint toolchain.

- **Not fixable.** The advisory range is `*` — every published version is
  affected, including the latest.
- **npm's suggested fix is a trap.** It proposes downgrading
  `eslint-config-next` to `14.2.35`, i.e. abandoning v16 tooling, and `npm
audit fix --force` will do it.
- **Not exploitable here.** It is a dev dependency, and the glob patterns it
  processes come from our own ESLint config, never from user input. Nothing
  reaches production.

Leave it. Re-check when `picomatch` ships a patched release.
